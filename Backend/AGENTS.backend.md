# Backend/AGENTS.md — Wallo Backend Instructions

## Scope

These instructions apply to the Wallo FastAPI backend.

The backend is Python 3.12+, FastAPI, SQLAlchemy 2.0 async, Pydantic v2, Alembic, PostgreSQL via asyncpg, Redis async cache, Enable Banking integration and scikit-learn/joblib for ML categorization.

## Core commands

Run from this backend directory:

```bash
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
pytest tests/ -v --cov=app
ruff check app/ --fix && ruff format app/
alembic revision --autogenerate -m "description"
alembic upgrade head
python -m scripts.train_base_model
python -m app.categories.tasks
```

Prefer targeted tests for small changes, for example:

```bash
pytest tests/auth/test_auth.py -v
pytest tests/banking/test_service.py -v
pytest tests/categories/test_service.py -v
pytest tests/transactions/test_transactions.py -v
```

## Backend architecture

Each domain should follow this shape:

```text
app/<domain>/
├── router.py    # FastAPI routes, HTTP concerns only
├── service.py   # business logic, DB queries, orchestration
├── models.py    # SQLAlchemy tables
├── schemas.py   # Pydantic v2 API input/output schemas
└── ...          # domain-specific helpers
```

Rules:

- Routers handle path/query/body parsing, dependency injection and response mapping only.
- Services contain all business logic.
- Models define database schema only.
- Schemas define API contracts only.
- Routers may import services and schemas.
- Services may import models and schemas.
- Models must not import routers or services.
- Do not place business logic in routers.

## API conventions

- All routes must be under `/api/v1/` via router registration in `app/main.py`.
- Use tags for OpenAPI grouping.
- Use Pydantic v2 schemas with separate Create, Update and Response models when relevant.
- Use `Annotated[type, Depends(...)]` for FastAPI dependencies.
- Use async route handlers and async service functions for I/O.
- Use sync functions only for CPU-bound work, such as ML training/prediction helpers when appropriate.

## SQLAlchemy and database rules

- Use SQLAlchemy 2.0 style: `Mapped[...]` and `mapped_column()`.
- Do not use legacy `Column()` for new models.
- Use async sessions via asyncpg.
- Preserve `expire_on_commit=False` session behavior.
- Use UUID primary keys generated by PostgreSQL where existing patterns do.
- Use timezone-aware timestamps.
- Monetary values must use `Numeric(12, 2)` and Python `Decimal`.
- Never use `Float` for persisted money.
- Respect naming conventions for `ix_`, `uq_`, `ck_`, `fk_`, `pk_`.

When adding a model:

1. Add the model in the correct domain.
2. Import it in Alembic env/model registry as needed so autogenerate sees it.
3. Generate and inspect the migration.
4. Add or update tests.

## Enable Banking rules

All Enable Banking calls must go through `app/banking/client.py`.

Do not create raw `httpx` calls to Enable Banking elsewhere.

Important domain constraints:

- API base URL: `https://api.enablebanking.com`.
- Authentication uses per-request RS256 JWT with the app ID as `kid`.
- Private `.pem` keys are loaded from backend `keys/` and must stay gitignored.
- App ID and private key path come from settings/environment.
- Never store user bank credentials.
- Bank authorization is redirect-based.
- Sessions can be valid up to 180 days.
- Fetch balances and transactions per account after session creation.
- Continue transaction pagination until `continuation_key` is null.
- Empty transaction pages can still include a continuation key; continue fetching.
- Bank fields vary; use optional-safe parsing.
- Parse amounts as `Decimal`.
- Balance priority: `ITAV` > `XPCD` > `CLBD`.
- On sync, preserve forwarding of PSU headers when supported by the existing code path.

## Categorization and ML rules

The transaction categorization system is a cascade. Preserve its order and fail-safe behavior.

Current conceptual cascade:

1. Rule-based type detection.
2. User merchant mapping.
3. Global merchant dictionary.
4. Keyword rules.
5. ML model prediction.
6. Confidence threshold / uncategorized fallback.

Rules:

- Manual corrections must set the transaction as manually corrected.
- User corrections should create or update merchant mappings for active learning.
- Do not overwrite manually corrected transactions during recategorization.
- ML model artifacts under `data/models/` are generated artifacts and should remain gitignored unless the repository explicitly tracks sample artifacts.
- Base training data is in `data/training_data.csv`; do not mutate it casually.
- If no trained model exists, categorization must degrade gracefully.

## Auth rules

- Passwords are hashed with bcrypt/passlib.
- JWT algorithm and secret come from settings.
- Do not hardcode secrets.
- Protected endpoints should use the existing current-user dependency.
- When changing auth responses, update frontend types and API consumption.

## Redis and caching rules

- Redis is optional; backend should continue when Redis is unavailable.
- Dashboard cache uses user-specific keys and short TTL.
- Invalidate dashboard-related cache when transaction, account, budget, recurring charge or report-relevant data changes.
- Never cache user-private data under non-user-specific keys.

## Reports, budgets and recurring charges

When changing financial calculations:

- Use date ranges carefully and make inclusivity explicit.
- Use `Decimal` for sums.
- Keep debit/credit sign conventions consistent.
- Ensure user ownership is checked on all resource operations.
- For recurring charges, respect dismissed charges and do not recreate them automatically.

## Testing expectations

For backend changes:

- Add unit tests for pure logic and service tests for DB/service behavior.
- Mirror the `app/` structure under `tests/`.
- Use pytest and pytest-asyncio conventions already present in the project.
- For DB-related changes, include ownership and authorization edge cases where relevant.
- For Enable Banking code, prefer mocked client behavior instead of live API calls.
- For ML/text-cleaning changes, add deterministic tests.

## Do not do

- Do not commit `.env` files.
- Do not commit `.pem` keys.
- Do not store bank credentials.
- Do not bypass `app/banking/client.py` for Enable Banking calls.
- Do not put business logic in routers.
- Do not use floats for persisted money.
- Do not create synchronous DB or HTTP I/O in async request paths.
- Do not silently change public API response shapes without updating frontend types.
